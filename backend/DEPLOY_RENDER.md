# Deploying the backend to Render (free plan)

`render.yaml` at the repository root defines two free web services, both built
from `backend/Dockerfile`:

| Service                | Branch    | Database          |
|------------------------|-----------|-------------------|
| `eye-care-api`         | `main`    | `eyecare_prod`    |
| `eye-care-api-staging` | `staging` | `eyecare_staging` |

The frontend stays on Vercel and the database stays on MongoDB Atlas.

## One-time setup

1. Sign up at <https://render.com> with GitHub. The free plan needs no card.
2. Click **New → Blueprint**, pick the `Eye-care-ERP` repository and the
   `main` branch. Render reads `render.yaml` and lists both services.
3. Render asks for `MONGODB_URL` for each service. Paste the Atlas connection
   string. `SECRET_KEY` is generated by Render.
4. Click **Apply**. The first build takes about 5 minutes.
5. In Atlas, **Network Access** must allow `0.0.0.0/0`, because Render's free
   plan has no fixed outgoing IP address.
6. Check each service at `https://<service-url>/health`.

After this, every push to `main` or `staging` that touches `backend/`
redeploys the matching service.

## Free plan limits

- **Sleep:** a service sleeps after 15 minutes without requests. The next
  request waits about a minute while it starts. The frontend's API client
  already waits and retries long enough for this.
- **750 free instance hours per month for the whole workspace.** If you use
  them all, *every* free service is suspended until the next month. Two
  services awake all the time would need about 1,440 hours, so don't keep both
  awake around the clock.
- **Keeping production awake:** Render's own health checks don't count as
  traffic. `.github/workflows/keep-awake.yml` calls `/health` on production
  every 10 minutes from 07:30 to 18:20 Sri Lanka time (change the `cron` line
  for other hours). That's about 340 hours a month and leaves the rest for
  staging. GitHub pauses scheduled workflows after 60 days without a commit to
  the repository; re-enable it under **Actions** if that happens.
- **No email over SMTP:** free services can't connect to mail servers on ports
  25, 465 or 587. The backend sends password-reset codes and purchase orders
  through Brevo's HTTPS API instead whenever `BREVO_API_KEY` is set (see Email below).
- **Instance size:** 512 MB RAM with a small CPU share, which is enough for
  one uvicorn process.

## Email (password-reset codes and purchase orders)

1. Create a free Brevo account (300 emails a day) at <https://www.brevo.com>.
2. Under **Senders, domains & dedicated IPs → Senders**, add and verify the address
   in `SMTP_FROM_EMAIL` (default `vision.opticals.lk@gmail.com`).
3. Under **SMTP & API → API keys**, create a key.
4. In the Render dashboard, set `BREVO_API_KEY` on both services
   (`eye-care-api` and `eye-care-api-staging`) and redeploy.

With no key set the backend uses Gmail SMTP (`SMTP_PASSWORD`), which works locally
but not on Render's free plan. If an email can't be sent, the reset screen still
says a code was sent (so it doesn't reveal which emails are registered), and the
error is in the service logs.

## First admin account (no shell needed)

Render's free plan has no shell, so the backend can create the first admin itself:

1. In the Render dashboard, open the service → **Environment** and add
   `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_NAME` and `BOOTSTRAP_ADMIN_PASSWORD`
   (a temporary password, at least 8 characters).
2. Save and let it redeploy. The log shows `Created admin ... from BOOTSTRAP_ADMIN_*`.
3. Sign in with that email and password; the app makes you choose a new password first.
4. Delete the three variables (and redeploy). An account that already exists is never
   changed, so leaving them set can't reset the password, but there's no reason to keep them.

Do it once per service: `eye-care-api` (database `eyecare_prod`) and
`eye-care-api-staging` (`eyecare_staging`).

Alternatively, run `scripts/create_admin.py` from your own computer with `MONGODB_URL`
and `MONGODB_DB_NAME` set. That connects to Atlas directly, so your IP must be on the
Atlas **Network Access** list.
